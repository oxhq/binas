# PDF Semantic Boundaries

The PDF object graph is the foundation for `binas`: it lets the adapter detect file shape, expose root metadata, find supported content-stream text nodes, and verify byte rewrites by reparsing the output. It is not a blanket guarantee that every object reachable from the graph is semantically editable.

The current edit contract is narrow: rewrite supported selectable `pdf.content.text_show` operands in supported content streams, update supported stream lengths, rebuild a basic xref table, and verify `reparse`, `old-gone`, `new-selectable`, `page-unchanged`, and `no-fallback-used`. AcroForm and annotation updates are separate semantic commands with their own smaller verification contracts.

## Fail-Closed Boundaries

These surfaces stop parsing before edit planning:

- Encryption: `/Encrypt` means encrypted object and stream bytes may need password-derived decryption. Without a password option the adapter/security layer returns `unsupported PDF: encrypted PDFs require an explicit password-capable path; Adapter.Parse does not decrypt`. The explicit password path supports Standard Security R2/R3/R4 RC4 and R4 AESV2 files with normal encrypted strings and streams, encrypted object streams inflated into graph objects, encrypted xref streams decoded before graph parsing, plus stream-level `/Crypt` filters for `/Identity` and `/StdCF`: it authenticates the password, decrypts into the object graph, supports `inspect`, `validate`, `query`, and canonical text edit, then re-encrypts strings and streams before writing. It still fails closed for unsupported handlers, public-key security, AESV3+, unsupported crypt filters outside that supported `/Identity` and `/StdCF` shape, and missing trailer `/ID`. Generic `Adapter.Parse` still has no password parameter and remains fail-closed for encrypted PDFs. Password values are inputs only and are not emitted in JSON or errors.
- Digital signatures: true PDF name tokens for `/Sig`, `/ByteRange`, or `/SigFlags` mean byte-range and digest semantics can be invalidated by ordinary rewrites. The signature boundary scanner skips literal strings, comments, and hex strings, then returns `unsupported PDF: digital signatures require explicit invalidation mode; Adapter.Parse refuses silent signature invalidation` for true markers.
- XFA in generic parse/edit: `/XFA` means form data may live in XML packets instead of normal AcroForm fields or page content streams. The default adapter returns `unsupported PDF: XFA forms are not implemented`; the explicit `xfa list` and `xfa replace` commands are the narrow packet-level exceptions. `xfa list` can report referenced stream packets with decode errors instead of silently omitting them, classify obvious packet kinds from labels or XML roots, expose conservative XML prolog/root diagnostics when safely detectable, and filter by exact `packet_kind` or array label. `xfa replace` skips literal/hex/name packet labels the same way `xfa list` does and can restrict matches by exact packet kind or label before ambiguity checks.
- Xref streams: these compressed xref carriers are detected in xref metadata. Parseable xref streams route through the object graph for generic parse, query, and supported rewrites; malformed or unsupported xref streams still fail closed with partial metadata when available.

Fail-closed means callers get a parser error instead of a partial edit plan. For malformed xref streams, `inspect --json` and `validate --json` can still include root metadata because the adapter can summarize that structural shape before rejecting it. Object streams are inflated into graph objects and canonical-written as normal indirect objects for the supported graph path.

Signature handling has three explicit modes: `refuse`, `invalidate`, and `preserve-incremental`. The default is `refuse`. `invalidate` is the canonical helper path: `ApplyCanonicalEditInvalidatingSignatures` and `binas edit --signature-mode invalidate` may canonical-write a signed PDF only when the caller deliberately chooses to invalidate signatures. The legacy `--allow-signature-invalidation` flag remains an alias for that invalidating path. Its verification remains honest but narrow: it reparses the produced object graph under the same invalidation mode and checks the text/page invariants; it does not claim that an existing cryptographic signature remains valid.

`preserve-incremental` is the append-only path for the supported signed text-edit shape. `ApplyIncrementalTextEditPreservingSignatures` and `binas edit --signature-mode preserve-incremental` require a table-xref PDF, no object streams, no xref streams, a raw/unfiltered content-stream target, and parseable nonnegative `/ByteRange` offset/length pairs inside the original file. The output preserves original bytes as a prefix, appends the updated stream object plus xref/trailer with `/Prev`, reparses with signature markers allowed, verifies the text/page invariants, and compares every signed byte range byte-for-byte. It reports that byte-range proof in JSON. It does not cryptographically validate signatures, re-sign, preserve unsupported signed shapes, or promise that every PDF viewer's policy will accept the incremental update. The default adapter parse and default canonical edit path still fail closed for `/Sig`, `/ByteRange`, and `/SigFlags`.

## Detection-Only Boundaries

These markers do not make the file invalid by themselves, but they do not become broad editable features:

- AcroForm: `/AcroForm` is reported as `has_acroform`. `form list` reports field indexes, fully qualified names, object ids, inherited field types, `type_flag_names`, direct alternate `/TU` names, direct mapping `/TM` names, inherited/direct `/Ff` field flags for `read_only`, `required`, and `no_export`, decoded `/V` values, direct default `/DV` values, kid counts, proven button widget appearance state, sorted proven button appearance states, and directly decoded choice-field `/Opt` options. `form set` updates exactly one matching field dictionary by exact or fully qualified parent/child field name. Text fields set a literal `/V` value and `/NeedAppearances true`; non-editable choice fields with proven direct `/Opt` options reject unlisted values; editable choice fields or choice fields without proven options accept literal values; proven checkbox/button fields set `/V` and `/AS` to `/Off` or the proven on-state from `/AP /N`, including inherited `/FT /Btn` and a narrow parent-field radio shape. `form set --regenerate-appearance` creates simple Helvetica widget `/AP /N` streams for text and choice widgets with proven direct `/Rect`, explicit newlines, approximate wrapping, clipping, and height truncation; buttons fail closed for regeneration. Field tree rewriting beyond matching/inherited type detection, broad default appearance interpretation, button appearance synthesis, and broad widget synchronization are not implemented.
- Annotations: `/Annots` is reported as `has_annotations`. `annot list` exposes candidate indexes, subtype, contents, indirect object id when present, `/AP` presence, direct `/NM` name, `/M` modified value, `/T` title, page index/object metadata when the candidate can be proven from a page `/Annots` array, direct four-number `/Rect` values when available, direct numeric `/F` annotation flags decoded into common flag names, direct numeric color and border metadata, and `quad_points_count`. `annot set-contents` updates exactly one annotation dictionary `/Contents` value by index. It preserves `/AP` by default; `--remove-appearance` explicitly removes stale annotation `/AP` and reports appearance invalidation/removal; `--regenerate-appearance` creates simple `/AP /N` Form XObject streams for supported text-like annotations with proven direct `/Rect`, explicit newlines, approximate wrapping, clipping, and height truncation. Popup state, highlight geometry editing, rich annotation appearance layout, and non-text-like appearance regeneration are not implemented.
- Font/CMap markers: `/Font`, `/CMap`, `/ToUnicode`, `/CIDFontType0`, `/CIDFontType2`, `/CIDToGIDMap`, and bare CMap stream markers such as `begincmap`, `beginbfchar`, and `beginbfrange` are summarized through the font/CMap boundary fields when detected outside PDF literal strings, comments, and hex strings. Text decoding supports simple literal operands, simple ASCII hex operands, literal/hex `TJ` arrays, page font-scoped `/ToUnicode` maps for simple `Tf` flows, CMap-backed hex `TJ` arrays, one unambiguous fallback map for hex operands, longest-match reverse CMap encoding for currently decoded strings, and conservative raw `width_units` metadata when direct simple-font `/FirstChar` and `/Widths` can be proven. Glyph substitution beyond those maps, full font metrics, visual layout, and reflow are not implemented.

For these limited-support boundaries, `validate --json` keeps `valid: true` and emits warnings. `inspect --json` exposes the boundary fields under `root.boundaries`. Residual boundary scanning skips PDF literal strings, comments, and hex strings for non-signature boundary name markers, reducing false warnings without making those surfaces editable. A supported content-stream rewrite may still run if the selected text node is one of the supported operands, but that command is not updating the corresponding high-level form, annotation, font, or visual semantics.

## pypdf Comparison Notes

A local pypdf checkout was sampled for comparison. It is a general Python PDF library with documented support for reading and writing encryption, decrypting encrypted files, adding annotations, reading AcroForm field structures, parsing `/ToUnicode` CMaps, and carrying font metrics for text extraction and appearance work.

That comparison should not be read as a requirement that `binas` mirror pypdf's scope. It clarifies the opposite boundary:

- pypdf-style encryption/decryption includes many handlers and crypt-filter cases. `binas` now has a public explicit-password path for Standard Security R2/R3/R4 RC4 and R4 AESV2 graph parsing, encrypted object-stream inflation, encrypted xref-stream decoding, supported content-stream text edits, stream-level `/Crypt` `/Identity` or `/StdCF`, and re-encryption, but it still rejects AESV3+, public-key security, and unsupported crypt filters outside that supported shape.
- pypdf-style signature handling can inspect and carry signature dictionaries. `binas` now has an explicit invalidating canonical path and a narrow append-only `preserve-incremental` path that proves original bytes and signed `/ByteRange` bytes are unchanged for supported raw content-stream text edits, but it does not perform cryptographic signature validation or re-signing.
- pypdf-style annotation support includes creating and writing annotation dictionaries. `binas` can list annotations with page metadata, direct `/Rect` values, direct common text metadata, decoded `/F` flags, direct numeric color and border metadata, and `quad_points_count` when proven from page `/Annots` arrays, update `/Contents`, remove stale `/AP`, and generate simple text-like `/AP /N` streams with approximate multiline layout, but it does not implement rich annotation layout or non-text-like appearance synthesis.
- pypdf-style AcroForm support reads form trees and has XFA-specific checks. `binas` can list AcroForm fields, direct alternate/mapping/default names, inherited/direct `/Ff` flags, `type_flag_names`, proven button states, and directly decoded choice options, update exact text field `/V` values, validate non-editable choice updates against proven direct options, update proven checkbox/button or narrow radio `/V` and `/AS` values, generate simple text/choice widget `/AP /N` streams with approximate multiline layout when requested and the widget has a proven direct `/Rect`, list directly represented XFA packets plus stream decode diagnostics, XML prolog/root diagnostics, decoded byte/text lengths, conservative kind classification, and exact packet-kind/label filters, and update exact directly represented XFA packets while skipping packet labels, but it does not implement broad field appearance or XFA package semantics.
- pypdf-style CMap/font support parses `/ToUnicode`, encodings, CID widths, and font metrics. `binas` supports page font-scoped `/ToUnicode` maps for simple `Tf` flows, CMap-backed hex strings and hex `TJ` arrays, longest-match reverse encoding for supported maps, one unambiguous fallback map for hex text matching/replacement, and conservative raw width metadata for direct simple fonts, but does not verify visual layout or full font semantics.

The useful near-term `binas` moat is therefore not broad PDF feature parity. It is fail-closed, span-preserving, verified rewrites for the subset that has explicit fixtures and command proof.

## Documentation Rule

Do not document a surface as editable until all of these exist:

- A focused fixture or real-file proof for that exact shape.
- Parser metadata that distinguishes supported from unsupported cases without broad string false positives.
- Edit planning that refuses ambiguous semantic ownership.
- Apply-time span and source-byte precondition checks.
- Verification that reparses the produced PDF and proves the user-visible invariant claimed by the feature.

Until then, keep the surface either fail-closed or detection-only with an explicit warning.
